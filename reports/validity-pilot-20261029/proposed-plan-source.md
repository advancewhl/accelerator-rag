# 面向科学工程系统的“有效性边界感知”检索与演进研究计划

## 一、 核心立意与研究主线

### 1.1 核心研究问题
在粒子加速器设计运维与 Waveform 数据分析等科学工程场景中，一个可执行的工程判断（如参数设定、对齐口径选择、故障排障）高度依赖其成立的**有效性边界（Validity Envelope）**——即该结论所绑定的**表头工况、前置安全条件、数值适用区间以及底层软件/硬件版本**。

现有 RAG 系统（包括通用混合检索、图检索与增量索引）面临两类核心失效：
1. **横向条件剥离（结构与完备性失效）**：传统切片将表格数值与表头工况、操作步骤与跨段落前置条件割裂；检索器仅按语义相似度召回孤立片段，导致回答遗漏关键限制条件或发生数值越界。
2. **纵向演化失配（版本与依赖失效）**：当底层接口、校准参数或对齐算法发生迭代时，现有增量索引仅追加新文档，无法识别哪些既有操作手册、历史排障结论和派生摘要的“版本有效性”已被打破，导致系统混用新旧版本知识。

### 1.2 统一方法主张
本研究不依赖重度模型训练或复杂黑盒算法，提出一套**基于工程有效性边界（Validity-Envelope Grounded）的结构化检索与持续维护框架**：
* **统一底座表示**：将工程文档解析为带有显式有效性边界（结构上下文、数值约束、适用版本与实体依赖）的证据单元。
* **维护期（纵向演化维护）**：基于受控工程实体与版本签名构建依赖关联，当文档或代码变更时，执行确定性的状态传播、过期知识隔离与局部摘要更新。
* **诊断期（横向完备检索与核查）**：在固定预算下按问题需求组合证据及其前置条件，并在生成前执行“版本—数值—完备性”核查，确保工程回答完整、合规、可追溯。

## 三、 核心模块设计与代码落点

所有新增能力均围绕“有效性边界”展开，直接落位至 `accelerator-rag` 仓库：

### 3.1 M0：运行身份冻结与完整资源计量（`scripts/rag_framework_metrics.py`, `rag/service.py`, `rag/runtime.py`）
* **机制**：严格绑定代码 Commit、模型版本、语料快照、索引签名与提示词；记录端到端及各阶段调用次数、文本/结构化 Token 开销与 P50/P95 延迟。
* **验收标准**：最终冻结代码通过旧 36 题全量回归；所有正式实验结果 100% 可追溯，严禁混入开发期缓存结果。

### 3.2 M1 + M2：带有效性边界的多粒度证据解析与索引（`corpus/pdf_parser.py`, `retrieval/index_contract.py`）
* **机制**：
  1. **结构与条件绑定**：扩展解析器，将表格行与表头/章节工况、流程图/波形图与图注及正文说明、操作步骤与前置条件绑定为不可分割的证据单元。
  2. **统一契约 Schema**：在 `index_contract.py` 中为每个证据单元附加两类结构化边界字段：
     - `condition_envelope`：所属子系统、运行模式、核心参数名、数值适用范围与单位、必需前置条件槽位。
     - `version_envelope`：来源文档/代码版本标识（`source_version` / Hash）、生效时间、生命周期状态（`ACTIVE` / `STALE` / `DEPRECATED`）、以及锚定在具体设备/接口/参数实体上的依赖列表（`depends_on_entities`）。
* **验收标准**：在 150 个双人抽检的代表性工程证据单元上，表头/图注/条件关联准确率 $\ge 95\%$；索引来源可还原率 100%；解析失败时平滑回退至原页面级块。

### 3.3 M6：受控依赖追踪与增量维护机制（新增 `maintenance/` 模块，落地 4 份 Waveform 核心文档）
* **机制**：
  1. **工程文档标准化**：建设并维护 4 份 Waveform 核心文档（存储与数据流说明、对齐语义与诊断手册、历史故障与版本变更记录、RAG 入库与回滚手册），明确标注接口签名与适用版本。
  2. **变更状态传播**：当底层文档、接口参数或对齐规则更新时，通过 Git/文档 Diff 定位变更的参数或接口实体，沿 `depends_on_entities` 检索受波及的上层手册段落、历史案例与派生摘要。
  3. **分级维护**：将受影响的派生摘要标记为 `STALE` 并仅对其执行局部重算；对基于旧版本逻辑的历史排障记录自动挂载 `DEPRECATED` 版本隔离说明（保留历史可供回溯，但阻断其作为当前默认操作指南被误用）。
* **验收标准**：4 类典型更新演练通过 `pytest`；更新后无悬空引用；相比全量重建索引，局部维护的调用成本或耗时降低 $\ge 50\%$。

### 3.4 M3 + M4：边界感知的证据组合与核查生成工作流（`RequirementRetriever.retrieve()`, `rag/context.py`, `answer.py`, `workflow.py`）
* **机制**：
  1. **互补证据组合检索（M3）**：在固定候选池与 Token 预算内，当召回包含核心数值或步骤的片段时，自动补全其关联的表头定义、前置条件块与版本说明，替换语义重复的冗余片段。
  2. **版本与条件核查门控（M4）**：在组织上下文与生成回答前执行三项确定性检查：
     - **版本对齐检查**：默认过滤 `DEPRECATED` 节点；若问题明确涉及历史故障或特定旧版本数据，则激活对应版本快照。
     - **数值与工况匹配**：核对提问中的工况与参数是否落在证据单元的 `condition_envelope` 内；若存在跨版本或跨工况差异，分情况并列说明，禁止强行融合。
     - **完备性与诚实部分回答**：若关键前置条件在当前证据集中缺失，明确输出已核实部分与缺失条件，并给出待查文档的精确页码/章节引用。
* **验收标准**：人工评定引用支持率 $\ge 95\%$；复杂条件与跨文档任务正确率显著提升，且简单事实题不发生超过 2 个百分点的退化。

## 四、 数据集建设与实验评估方案（降本增效设计）

为避免纯人工盲评带来的高昂负担（原估算 99～164 人日），采用**“核心集双人精标 + 确定性评分契约（Checklist Rubrics）半自动验证”**机制，将标注与评测总人工控制在 **45～65 人日**。

### 4.1 数据集规划
| 数据集名称 | 规模 | 构成与用途 |
| :--- | :--- | :--- |
| **1. 探索与校准集（Dev Set）** | **90 题** | 分为结构条件（30 题）、表格与图表关联（30 题）、版本变更与维护（30 题）。用于前 4 周原型验证、失败归因与自动评分器校准，**严禁进入正式测试结果**。 |
| **2. 加速器与 Waveform 独立测试集** | **240 题** | 覆盖参数条件恢复（60 题）、跨文档/子系统配置对比（60 题）、历史故障归因与检查步骤（60 题）、Waveform 对齐口径选择与越界陷阱诊断（60 题）。 |
| **3. 动态版本演进测试集** | **30 个变更事件**<br>（约 90 道关联题） | 采集自 Waveform 迭代历史（含国庆后对齐修复等案例）、加速器文档修订及 1 个开源工程文档库的 Git 历史。每个事件包含：变更前查询、变更后防过期查询、历史版本回溯查询。 |
| **4. 跨领域迁移与公开基准** | **150 题 + 抽样公开集** | 第二工程领域独立测试集（150 题）+ 1 个公开多文档/结构化基准固定抽样（300～500 题），验证方法非加速器特例。 |

### 4.2 对比基线与消融设计
* **对比系统（统一生成模型与可比预算预算）**：
  1. **强混合检索 + 重排**（BM25 + 双路向量 + RRF + Cross-Encoder，对标 APS-RAG 同等架构）。
  2. **图增强与增量检索系统**（HippoRAG 2 / LightRAG）。
  3. **版本感知检索基线**（VersionRAG 或带显式时间/版本元数据过滤的混合检索）。
  4. **多模态/页面级文档检索基线**（针对含图表与复杂表格的子集进行对比）。
* **核心消融实验**：
  1. **w/o 结构与条件包络（移除 M1/M2 绑定）**：退化为普通固定窗口切片。
  2. **w/o 依赖传播与状态隔离（移除 M6）**：文档更新时仅做普通增量追加，不标记 `DEPRECATED/STALE`。
  3. **w/o 互补组合与生成前核查（移除 M3/M4 门控）**：直接取 Top-$k$ 重排结果生成答案。
  4. **资源受控对比**：在严格相同的 Token 预算与调用次数上限下比较质量—成本曲线。

### 4.3 评价指标与统计规范
* **准确性与安全性指标**：任务回答正确率、关键前置条件完整率、过期知识误用率（Stale Hallucination Rate）、引用支持率（Citation Support）。
* **效率与维护指标**：单次变更的平均更新耗时与 Token 成本下降比例、端到端推理延迟（P50/P95）。
* **领域实用性评测（小规模专家实验）**：邀请 8～12 名具有加速器或相关工程背景的人员，在交叉设计（Crossover Design）下完成真实排障与 Waveform 对齐条件核查任务，对比任务一次成功率与查证耗时。
* **统计检验**：主要二元指标采用配对检验（McNemar / 聚类 Bootstrap，按文档或变更事件聚类避免样本伪独立），报告效应量与 95% 置信区间；人工与自动 Checklist 评分一致性需达到 Cohen's $\kappa \ge 0.75$。

## 五、 16 周分阶段执行排期与止损节点（Gatekeepers）

将研发周期分为四个紧凑阶段，设立两次明确的检查与决策点：

| 阶段 | 周次 | 核心任务 | 产出与决策/止损标准（Gate） |
| :--- | :--- | :--- | :--- |
| **阶段一：语料审计与最小原型验证** | **第 1–4 周** | 1. 完成 **M0 冻结**与旧 36 题回归。<br>2. 落地 **Waveform 4 份核心文档**初版，梳理至少 20 个真实变更事件。<br>3. 构建 **90 道探索题**（附评分 Checklist），跑通基础混合检索、现成图检索与最小有效性边界原型。 | **第 4 周末 Gate 1（立项验收）**：<br>确认探索集上存在明确的“条件遗漏、表格割裂、版本过期”失败分布；最小原型在目标子类上展现出 $\ge 8\%$ 的改进潜力。若某子类无真实痛点，立即裁剪该支线。 |
| **阶段二：核心模块研发与正式集构建** | **第 5–9 周** | 1. 完整实现 **M1/M2（有效性边界解析与索引）**、**M6（变更传播与隔离）**、**M3/M4（互补组合与核查门控）**。<br>2. 完成 240 道正式工程题、30 个完整变更事件及 150 道第二领域题的构建与双人 Checklist 审核。<br>3. 校准自动评分器（验证 $\kappa \ge 0.75$）。 | **第 9 周末里程碑**：<br>核心代码冻结并通过单元测试（`pytest`）与回归测试；正式测试集与评分契约冻结，后续严禁针对测试集调参。 |
| **阶段三：全量对比实验与专家任务评测** | **第 10–13 周** | 1. 部署全部对比基线，在两个生成模型上运行正式主实验、动态演进实验与四项消融实验。<br>2. 收集完整资源开销与延迟数据（M5），绘制质量—成本曲线。<br>3. 组织 8～12 名领域人员完成真实场景查证与排障对比实验。 | **第 13 周末 Gate 2（投稿分流决策）**：<br>拿到全部冻结实验统计表，根据跨领域方法收益与领域专家任务收益的相对强弱，确定最终主打期刊。 |
| **阶段四：论文撰写、复现核查与定稿** | **第 14–16 周** | 1. 开展失败案例归因分析，撰写论文正文，绘制系统架构图与实验图表（共 6 张主图）。<br>2. 执行独立内部审阅与脚本一键复现核查。 | **第 16 周末交付**：<br>完成具备直接投稿质量的完整稿件与可复现实验包。 |

## 六、 投稿目标动态适配策略

依托同一套系统底座与实验数据，在第 13 周根据实测结果顺畅对接目标期刊：

1. **主攻路线 A：ACM TOIS 或 IEEE TKDE（计算机顶刊）**
   * **适用条件**：跨领域测试集与公开基准上的有效性核查收益、以及 30 个变更事件上的局部维护成本优势均达到统计显著。
   * **叙事重心**：突出**“面向演进工程文档的有效性边界表示、依赖驱动的增量维护与受约束证据组合机制”**；将加速器和 Waveform 作为核心高可靠工程验证场景（若维护与演化实验最出彩，优先投 TKDE；若结构化检索与证据组合实验最出彩，优先投 TOIS）。
2. **主攻路线 B：Physical Review Accelerators and Beams (PRAB，加速器旗舰期刊)**
   * **适用条件**：在加速器设计运维与 Waveform 分析任务上正确率与条件完整率提升显著，且 8～12 名领域人员的任务评测证明查证时间明显缩短、排障可靠性提高。
   * **叙事重心**：突出**“面向加速器诊断、运行维护与波形分析的可追溯知识辅助系统”**；重点展示如何解决物理工程参数表割裂、跨运行周期版本混用与对齐口径选择问题，用真实运维案例和同行测试数据说话。
