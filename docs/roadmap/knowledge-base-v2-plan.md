编制日期：2026 年 11 月 2 日。计划修订：`2026-11-02-r1`。状态：设计方案，尚未实施。

目标版本暂定为 `kb-2.0.0`。本文覆盖现有知识库和当天新增资料，从资料治理、解析扩展、版本检索，一直到候选构建、验收、生产切换及上线观察。`kb-2.0.0` 表示知识库发布版本，不代表原始文档版本或软件包版本。

## 1. 总体决策与交付目标

本次扩建应形成一套**支持多种资料、能够识别适用版本、可以成套发布和回滚的知识库**。扩充文件格式与建立版本管理必须一起完成，否则资料增加后，旧设计、修订稿和现场口径更容易混用。

采用以下设计：

1. 保留原始资料，另建规范化内容和阅读副本。Word、PPT、表格各用适合其结构的解析方式。
2. 分开管理文档族、具体修订、派生文件、构建结果和知识库发布。每条回答能追溯到具体修订与原文位置。
3. 检索先判断设备、用途、时间和版本适用性，再计算相关性。最新收件、最新文件名不等于当前有效。
4. 沿用 BM25、双路向量召回、重排和有界证据闭环。首版不同时更换生成模型和嵌入模型，以便定位质量变化。
5. 在独立候选目录构建完整发布包。代码、原文、元数据、两路索引和阅读器一起切换，失败时一起回退。
6. 先建立可用的工程版本规则。动态依赖传播、知识图谱和复杂研究模块按 [PRAB 计划](../../PRAB_PLAN.md)另行验证，不作为本次上线前提。

新版本交付完成，至少要满足以下条件：

- 218 个输入文件均有去向记录；合并、暂存和排除都有理由。
- PDF、Markdown、DOCX、DOC、PPTX 和选定的结构化表格走通入库、查询和引用链路。
- 现行、历史、参考和待核实材料有明确使用规则，支持指定版本查询和版本比较。
- 原有 17 份资料纳入发布管理，既有问答和旧引用的兼容策略经过验证。
- 通过资料、索引、问答、阅读器和部署验收；实际完成生产切换与观察期。
- 留下发布说明、验证结果、完整回退版本和维护手册。

## 3. 资料类型与纳入策略

### 3.1 文件格式、业务类型和主题分别管理

原来的 `document_type` 表示文件格式。新设计保留兼容映射，另外增加业务类型和适用主题，避免把“PDF”“操作手册”“联锁系统”混成同一个分类。

| 分类轴 | 主要取值 | 用途 |
| --- | --- | --- |
| 文件格式 `source_format` | PDF、MD、DOCX、DOC、PPTX、XLSX、CSV、ODS、TXT、图片、压缩包 | 选择解析器和阅读器 |
| 业务类型 `document_kind` | 总体设计、分系统设计、标准规范、接口说明、操作手册、安装维护、测试大纲、测试报告、验收报告、研制总结、评审意见、会议记录、论文、配置快照、结构化清单、图纸 | 判断证据用途和权威范围 |
| 学科与子系统 | 沿用现有 `category`、`topic`，按资料补充网络、数据存储、报警、电源、真空、激光、运动控制、网络安全等主题 | 目录筛选和检索范围 |
| 适用范围 `scope` | 装置、子系统、设备族、位置、软硬件版本、运行模式 | 避免跨设备或跨阶段误用 |
| 证据性质 `evidence_role` | 设计指标、规范要求、测试结果、验收结论、操作步骤、历史记录、背景参考 | 区分“要求达到”与“已经测得” |

主题扩展通过受控词表完成，并维护同义词。首次标注允许主主题和多个辅助标签，不强迫跨系统报告只属于一个主题。不能只根据文件夹名或文件名自动判定业务类型。

### 3.2 各格式的上线范围

| 资料 | `kb-2.0.0` 目标能力 | 证据定位 | 暂不承诺的能力 |
| --- | --- | --- | --- |
| 文本 PDF | 保留现有链路，补充表格和章节信息 | 原文件物理页、区域、章节 | 对所有复杂版式自动无损恢复 |
| 扫描及混合 PDF | 页面级 OCR、复核记录、阅读原页 | 原文件物理页、区域 | 未复核的关键数值直接作答 |
| DOCX | 原生提取标题、段落、表格和图注；生成阅读副本 | 原段落或表格锚点；可靠时附派生 PDF 页码 | 将任意转换页码当成原 DOCX 固有页码 |
| DOC | 固定转换环境，转为 DOCX 后复用解析；保留原件 | 原文件身份、转换后结构位置 | 原地覆盖旧文件 |
| PPTX | 按幻灯片提取标题、文本框、表格、图注和备注 | 幻灯片序号、对象位置；备注单独标识 | 从图片自动推断未写出的工程关系 |
| Markdown、TXT | 保留标题、列表、代码、表格；纯文本保留行号 | 章节锚点、行号 | 把章节序号显示为 PDF 页码 |
| XLSX、CSV、ODS | 完成选定端子表等结构化试点，按列名和行记录检索 | 工作表、单元格范围或 CSV 行列 | 任意表格计算、外部链接或宏执行 |
| 图纸和图片 | 目录登记、附件阅读、经复核的图注 | 页码或图片区域 | 首版自动理解电路拓扑、接线关系 |
| 代码、日志、配置 | 必要时作为版本化附件或只读配置快照 | 文件行号、来源版本、采集日期 | 自动执行脚本或把历史配置当成实时配置 |
| ZIP、RAR | 容器登记；需要时展开子文件并沿用相同审查 | 容器与内部路径 | 将压缩包本身当作正文索引 |

Office 转 PDF 用于阅读和交叉检查，不作为唯一解析策略。格式转换会损失段落层级、表格结构和备注，必须保留原生结构。

| 批次 | 内容 | 完成要求 |

## 4. 目标架构与数据流

采用离线构建、在线只读的架构。现有规模先使用文件化清单和现有本地索引，不新增分布式任务平台或独立元数据数据库。

| 层次 | 输入 | 输出与职责 |
| --- | --- | --- |
| 原始资料层 | 收件批次、原始文件 | 不可变原件、来源记录、收件日期和访问范围 |
| 资料治理层 | 原件、历史登记表 | 文档族、修订、重复关系、版本状态和入库决定 |
| 解析与转换层 | 已登记修订 | 结构化正文、表格、公式、图注、OCR 结果和阅读副本 |
| 证据层 | 规范化内容 | 带版本、位置和适用范围的父块及表格记录 |
| 索引层 | 同一批规范证据 | BM25 运行输入、两路向量索引、各路构建报告 |
| 问答服务层 | 用户问题、版本选择、发布快照 | 适用范围筛选、召回、重排、证据核查、回答 |
| 阅读与运维层 | 引用、发布清单、请求记录 | 原文定位、版本浏览、质量追踪、发布和回滚 |

资料按“接收、分类、确认版本、解析、复核、切块、构建、验收、发布”顺序流转。每一步保留输入身份和输出身份，失败结果回到对应步骤修复，不跳过问题继续发布。

建议增加以下目录。除现有 `data/l0_raw/` 外，下列新目录和文件均为设计目标，尚未创建。

| 位置 | 内容 | 管理方式 |
| --- | --- | --- |
| `data/l0_raw/incoming/<batch-id>/` | 收件原件 | 只增不覆盖，不进入 Git |
| `data/documents/v2/` | 文档族、修订、关系、处置记录和 Schema | 可审阅的元数据进入 Git；受限信息另行存放 |
| `data/knowledge-builds/<build-id>/` | 规范化结果、阅读副本、位置映射、父块及构建记录 | 构建产物，不进入 Git |
| `config/knowledge-releases/` | 发布配置模板和 Schema | 进入 Git；不保存凭据 |
| `reports/knowledge-base-v2/` | 解析质量、评测、迁移、上线和回滚报告 | 保存必要结果，避免重复大文件 |
| `/opt/accelerator-rag-releases/<release-id>/` | 生产发布包 | 原文、元数据、代码、索引和配置成套冻结 |

生产运行所需文件必须位于发布包或明确固定的共享模型目录。服务不能依赖开发机的绝对路径，也不能在运行中读取正在编辑的 `docs/` 文件。

## 5. 文档身份、修订与发布版本

### 5.1 分清五种身份

| 身份 | 含义 | 变化规则 |
| --- | --- | --- |
| `family_id` | 同一逻辑文档的版本族 | 第一版、第二版、第三版操作手册归入同族 |
| `revision_id` | 一份具体、不可变的来源修订 | 原始内容变化产生新修订，旧修订保留 |
| `asset_id` | 原件、转换件、OCR 结果或阅读副本 | 转换器或 OCR 变化可产生新派生资产，不伪造来源修订 |
| `build_id` | 一次固定处理规则的构建 | 解析、切块或索引配置变化产生新构建 |
| `release_id` | 用户实际使用的一整套知识库 | 通过验收并发布后产生新版本 |

建议发布号采用 `kb-主版本.次版本.修订号`，候选版加 `-rc.1` 等后缀。主版本用于不兼容契约变化；次版本用于语料扩充或查询能力变化；修订号用于兼容修正。每次重建都使用独立 `build_id`，已经发布的同名目录保持不变。

文档原有的“V6”“第三版”“2025 归档”等作为 `revision_label` 原样保存，不转换成知识库发布号。

### 5.2 兼容现有文档 ID

为了避免大范围重命名，现有 17 份资料的 `document_id` 暂作为对应修订的 ID 保留。新增 `family_id` 用来关联逻辑文档；新的修订获得新的 `revision_id`，并作为新检索记录的 `document_id`。

以某操作手册为例，逻辑族可命名为 `shine-timing-operation-manual`。已确认的第三版修订可命名为 `shine-timing-operation-manual-r3-202411`。具体日期和版号必须来自原件或责任人确认，不能为凑齐 ID 编造日期。

按修订 ID 构建和清理索引，禁止用逻辑族 ID 调用现有逐文档替换方法。否则导入第三版时会删除第一版、第二版，破坏历史查询。

建立旧 ID、旧来源路径和旧引用到冻结资产的映射。新引用同时绑定发布号与修订 ID，禁止将历史引用自动跳转到“最新版”。对于无法唯一确定的旧引用，明确提示版本不明，不静默选取新版本。

### 5.3 元数据契约

先定义 Schema v2，并在清单加载边界验证一次。解析、切块、索引和问答模块使用已校验的类型，不在各层重复解析原始字典。

| 字段组 | 主要字段 | 填写规则 |
| --- | --- | --- |
| 身份 | `family_id`、`revision_id`、`title`、`revision_label` | 标题可修正；身份保持稳定 |
| 来源 | `batch_id`、`original_asset_id`、`source_path`、`source_format`、`language` | 原件与转换件分开记录 |
| 分类 | `document_kind`、`category`、`topic`、`tags`、`evidence_role` | 使用受控词表，允许跨主题 |
| 时间 | `received_at`、`document_date`、`effective_from`、`effective_to`、`date_precision` | 月级日期保留月级精度，不自动补成某日 |
| 适用范围 | `scope`、`applicable_versions` | 装置、子系统、设备、用途、软硬件版本分别记录 |
| 文档状态 | `approval_status`、`usage_status` | 批准状态与知识库使用方式分开 |
| 权属与访问 | `owner`、`source_authority`、`access_scope` | 责任人、证据出处与可访问群体明确 |
| 关系 | `supersedes`、`equivalent_to`、`contains`、`supplements`、`derived_from` | 记录关系证据及适用范围 |
| 处理记录 | `parser_profile`、`conversion_profile`、`ocr_profile`、`review_record` | 标记人工确认与自动提取 |
| 使用决定 | `disposition`、`reason`、`reviewed_by`、`reviewed_at` | 入库、历史、附件、暂存、排除都有理由 |

未知字段使用明确的空值或 `unknown`。必填字段缺失时，该材料留在待治理区；不要用文件修改时间填生效日期，也不要用“最新”掩盖日期缺失。

版本、状态和生效时间等人工判断，需要附依据位置。后续修正元数据时保留修订记录，并在新发布中生效；旧发布仍保留当时的元数据快照。

### 5.4 状态与适用规则

| 状态维度 | 取值示例 | 语义 |
| --- | --- | --- |
| 来源批准状态 | `approved`、`draft`、`unknown`、`withdrawn` | 文档是否获批，是否撤回 |
| 知识使用状态 | `current`、`historical`、`reference`、`pending_review`、`excluded` | 在知识库中的使用角色 |
| 构建状态 | `received`、`parsed`、`reviewed`、`indexed`、`verified`、`failed` | 工程处理进度 |
| 发布状态 | `candidate`、`accepted`、`live`、`rolled_back`、`retired` | 是否已向用户提供服务 |

`current` 只对已确认的适用范围成立。同一文档族可以针对不同设备版本存在多个现行修订。若两个修订在相同范围内冲突，而缺少替代依据，应保留冲突并要求澄清，不能简单选日期较新的一份。

历史版本不等于错误材料。它仍可回答指定年份、旧设备、故障追溯和版本比较问题。参考论文也不能因不是现行操作规程而整体屏蔽；它可支持背景和研究结论，但不能替代现场操作依据。

待核实材料允许作为显式选择的参考来源。回答必须说明其状态；它不能单独支持“目前已经部署”“现行必须如此”等结论。

## 6. 重复、版本族和冲突治理

### 6.1 四类重复分别处理

| 类型 | 处理方式 | 保留信息 |
| --- | --- | --- |
| 完全相同的文件 | 共享原始资产，保留多个收件位置 | 所有来源和批次 |
| 同一内容的扫描版与文本版 | 优先文本版解析，扫描件供核对 | 等价关系、签发信息和原页 |
| 合并版与单项版 | 优先选定一个检索主来源，建立章节映射 | 包含关系与原始独立标题 |
| 同主题不同修订 | 保留各修订，建立版本族 | 版本差异、适用范围和替代依据 |

同名不自动合并，正文相似也不自动判为同一版本。验收意见、签发信息、附表或修订记录不同，可能改变证据含义。

已有重复分析用于生成候选组。只对会影响合并决定的文件做必要确认；不重复对全库执行低收益完整性检查。超过 64 MiB 的文件如需认定完全重复，应另做完整内容确认，不能复用前缀指纹作为结论。

### 6.2 本批必须建立的版本族

- 加速器总体设计：既有初步设计、优化设计 V6、控制章节之间的范围关系。
- 操作手册：第一版、第二版、第三版与归档副本之间的关系。
- 分系统设计：初步设计、技术设计、后续研制总结之间的关系。
- 标准规范：2024 合并版、5 份单项规范和扫描副本之间的关系。
- 测试与验收：测试大纲、自测、正式测试、验收书和评审意见之间的证据链。
- IOC、定时、网络和数据存储：历年说明与对应软件、设备版本的关系。

“技术设计晚于初步设计”只能生成待核实的替代候选。确认替代关系时，记录替代整篇、指定章节，还是仅替代某个指标。

首版默认在文档或章节层维护适用关系。只有真实冲突需要时，才下沉到具体表格或条目；不预先为全库建立逐句依赖图。

### 6.3 冲突台账

每项冲突至少记录主题、两侧修订、证据位置、冲突类型、适用条件、责任人和处置结果。

优先处理设计能量口径、定时设计指标与实测结果、联锁响应时间的测量范围、IOC 软件版本和不同版操作步骤。先核对设备与测量条件，再判断是否真正冲突。

未解决的冲突可以保留在历史或参考检索中，但不得产生单一的“当前确定答案”。涉及首版核心任务的冲突无法处理时，应阻止相应任务上线，或明确缩小本次发布范围。

## 7. 解析、规范化与证据定位

### 7.1 统一中间表示

新增与格式无关的 `ParsedDocument`，内部使用带类型的块。至少包含标题、段落、列表、表格、代码、公式、图注和图片引用。

每个块保留 `revision_id`、`asset_id`、`block_id`、章节路径、来源位置、提取方式和复核状态。阅读副本页码与原始来源位置单独存储。

现有 Markdown 借用 PDF 数据结构，并将章节序号放入页码字段。迁移时增加显式位置类型：`pdf_page`、`section`、`paragraph`、`slide`、`cell_range`、`line_range`。旧字段仅在兼容层保留，业务层不得继续把所有位置当成页码。

### 7.2 原生解析与阅读副本

DOCX 优先按正文顺序提取段落和表格，保留标题级别、编号、表头、脚注与图注。页眉页脚等重复内容可在清洗层处理，但要保留承载版本信息的封面和修订表。

DOC 使用固定的 LibreOffice 转换环境。原件、转换结果、工具版本、字体环境和失败信息都进入构建记录。当前环境中出现过沙箱转换限制，正式构建应使用经过样本验证的构建环境，而不是假定本机转换一定可用。

PPTX 按幻灯片和对象处理，备注标记为备注，不能拼成正文假装来自画面。PPT 阅读副本应验证幻灯片序号与预览页一一对应。

DOCX 的原生段落与 PDF 阅读页需要经过映射验证。无法可靠映射时，引用段落或表格锚点，提供原件及结构化阅读入口，不编造 PDF 页码。

超过普通文件规模的 V6 先单独试运行，记录内存、转换时长和各章节输出。全量抽取可以按章节安排，但要保留跨章节引用和表格标题，不能仅取开头若干页。

### 7.3 OCR 与公式

OCR 只处理确有正文而缺少文本层的页面或区域。对混合 PDF，保留已有可靠文本，避免整本重复识别引入新错误。

所有 OCR 关键参数、设备标识、单位、比较关系和表格映射均需核对原页。普通正文按页面类型抽样；抽样发现系统性错误时，扩大同类页面复核范围。字符数和 OCR 置信度只能辅助筛选，不能代替正确性判断。

数学内容按用户统一要求处理：可编辑数学表达保存有效 LaTeX 源码，并通过兼容 LaTeX 的渲染器显示。DOCX 公式转换、OCR 公式转写和表格公式展示均遵循这一规则。复核上下标、分式、运算符、定界符和对齐，并检查字号与裁切。

原始第三方文件保持原样。对无法可靠恢复的公式区域，保留原页供核对，并标记为未验证；不生成伪造公式，也不让该区域独立支持需要精确公式的答案。

### 7.4 表格与结构化记录

普通文档表格保留表名、列名、单位、合并单元格关系和脚注。切块时，每组数据行携带必要表头与适用条件；跨页续表先恢复关联，再形成证据。

端子表试点使用独立表结构，先确认设备、端子、信号、位置和版本字段的实际含义。检索返回完整记录和单元格定位，避免把不同版本的相邻行拼在一起。首版提供精确筛选和解释，不开放任意 SQL 或任意计算。

电子表格中的公式表达、缓存结果和计算状态分别保留。首版优先使用静态表格；需要公式结果时，在受控环境重算并核对。无法确认计算状态的值不用于精确结论，宏与外部链接不在导入中执行。

### 7.5 切块与质量复核

按章节、操作步骤、幻灯片和表格记录切分，父块保留适用范围与来源。不要把条件和结论、表头和数据、步骤和警告分离。

原有 PDF 块尽量沿用已验证规则。确需调整解析或切块时，使用新的处理版本，记录块 ID 变化，并更新评测中的等价证据映射，不能继续使用旧父块 ID 计算新版本覆盖率。

每种首版格式至少选 2 份代表资料；稀有格式按实际文件数覆盖。对大文档检查开头、中部、结尾、关键表格和版本相关章节。所有作为发布验收依据的关键参数与操作步骤都逐条复核，避免用“每份前 10 页”替代结构性检查。

## 8. 版本感知检索与回答

### 8.1 查询模式

| 模式 | 行为 | 典型用途 |
| --- | --- | --- |
| 默认查询 | 按任务范围选择现行依据；背景资料允许带性质使用 | 当前设计、规范和操作说明 |
| 指定版本或时间 | 使用明确修订或有效时间范围 | 旧设备、历史配置、故障回溯 |
| 版本比较 | 分别检索各版本，按差异项组织证据 | 新旧指标、步骤或接口变化 |
| 显式参考查询 | 用户选择待核实或过程资料，显示状态 | 查阅修订稿、评审意见和未确认材料 |

“某日有效的文档”与“某次知识库发布当时知道什么”分开表达。前者依据文档有效时间，后者选择冻结的 `release_id`。收件日期不能替代这两类时间。

问题缺少关键设备或版本时，只在这些缺口会改变答案的情况下澄清。能够给出共同成立部分时，先给部分答案，再说明缺少的信息。

### 8.2 同一规则覆盖所有召回路径

在单次请求入口生成统一的 `RetrievalScope`，包含发布号、允许的修订集合、主题、任务用途和访问范围。

BM25、两路向量检索、同页补全、表格检索和第二轮补检索都使用该范围。版本筛选应在各路选取候选前执行。先取前若干条再丢弃旧版本，会让合格证据挤不进结果，不能作为正式实现。

向量存储 payload 需要补齐修订、文档族、状态和适用范围等索引字段。BM25 使用相同的合格父块集合或等效的候选筛选。相邻块补全只补同修订的内容；版本比较则显式建立两组证据，不能混入同一结论。

默认保持两路向量集合的完整语料快照，以元数据选择范围。首版不按文件格式或每种业务类型拆成大量集合。只有实际隔离要求或测量结果证明必要时，再调整物理索引布局。

### 8.3 答案与引用

引用至少展示文档标题、原始版本标签、来源位置和资料性质。历史、草稿、OCR 未确认区域等状态要在读者需要判断适用性的位置说明。

关键事实关联其具体证据，而不是用一个整篇文档引用覆盖所有断言。设计指标、测试结果、验收结论和实时状态分别表述；存在不同口径时分别列出，不通过平均或择新制造统一结论。

响应增加 `release_id`，引用增加 `revision_id`、`asset_id` 和位置类型。请求记录保存实际使用的修订及筛选理由，支持从错误回答追查到资料、解析、召回或生成环节。

保持现有部分回答能力。证据缺失应表述为“本次资料不能确认”，不能扩大为“该能力不存在”或“现场没有部署”。

## 9. 目录、阅读器与接口改造

### 9.1 用户可见行为

- 目录支持主题、业务类型、格式、版本状态和适用系统筛选。
- 同一文档族展示版本列表，显示当前选用依据及其他可查版本。
- 目录区分可检索资料与仅供阅读的附件，并说明暂未入索引的原因。
- 引用可定位到 PDF 页、Markdown 章节、DOCX 段落、PPT 幻灯片或表格单元格。
- 页面显示当前知识库发布号和发布日期；历史发布的引用继续指向原修订。
- 版本比较先提供元数据及相关证据并列，不要求首版实现整篇文档的复杂可视化差异。

### 9.2 接口契约

保留现有 `/v1/rag/answer` 和 `/v1/rag/documents` 的兼容入口。查询模式、版本范围等可作为新增可选字段；未传时使用默认策略。现有请求模型禁止未知字段，因此必须同步更新 API、前端和契约测试，不能直接由前端附加参数。

新增或扩展以下能力，具体 URL 在接口设计阶段冻结：

| 能力 | 输入或输出要点 |
| --- | --- |
| 发布身份 | 返回 `release_id`、构建号、文档族数、修订数、可检索数和只读附件数 |
| 文档族与修订列表 | 按族查询各修订、状态、范围和替代关系 |
| 固定修订阅读 | 使用发布号、修订和资产定位，不依赖可变文件名 |
| 结构化证据定位 | 返回章节、幻灯片、单元格和对应阅读信息 |
| 问答范围 | 指定查询模式、修订、有效时间和系统范围 |

历史发布的资产需要保留明确的只读访问路径。首版不要求同时常驻多个历史问答服务；需要重现旧查询时，可以从冻结包启动对应版本。

### 9.3 访问范围

网络安全设计、地址表和内部配置可能与现有论文资料具有不同访问范围。先由资料责任人确认允许使用群体，再决定能否进入当前服务。

首版优先沿用现有受控内网部署边界。若无法对某些资料实施所需访问隔离，就将这些资料保留在受限待处理区，不让其进入公共目录、搜索片段、下载接口或回答日志。确有分用户权限需求时，再把统一鉴权与检索过滤列为上线前置工作。

## 10. 构建、发布清单与迁移

### 10.1 从专用脚本转向批次构建

现有 `build_markdown_index.py` 用于 Markdown 增量更新，不应直接扩成隐式操作整个生产库的脚本。新增通用构建入口，按批次和发布候选工作。

构建入口应支持：清单验证、范围预览、解析、质量报告、证据生成、两路索引构建、候选验证和发布包导出。具体命令在实现后写入运行手册，本文不提供尚不存在的可执行命令。

构建任务保存阶段结果，失败后从已完成阶段继续。修复某一解析器后，只重建受影响资产；跨版本的处理结果不能混用。单篇失败可以先完成其他独立解析，但候选冻结前必须修复或明确移出范围，不允许静默跳过。

### 10.2 新旧语料迁移

1. 以实际服务核对原有 17 份资料、原文路径、代码快照和两路索引，登记为迁移基线。
2. 从基线原文建立不可变修订，补充文档族与资料性质。已有 `active` 状态先映射为历史系统标签，不能自动宣称已经核实其现场适用性。
3. 建立新批次的逐文件处置清单，确认重复、版本族和准入范围。
4. 生成 Schema v2 元数据、规范化证据及阅读资产，保留旧 ID 映射。
5. 在独立候选目录构建包含旧语料与新增语料的完整快照。
6. 运行迁移验收，核对保留、增加、修订、合并、转历史和排除的差异。

新版本升级元数据和身份契约，默认进行一次完整候选构建。若样本测量表明成本过高，可按契约复用未变化向量，但必须生成新的完整发布快照，并验证复用内容。不能为了节省构建时间，在在线索引上混合新旧 Schema。

首次迁移之后，采用按修订增量构建。源文件变更、新增修订、撤回、元数据变化和解析器变化分别确定重建范围；最终仍交付完整一致的发布清单。

### 10.3 发布清单

每个候选生成 `release-manifest.json`。清单至少包含以下内容：

| 部分 | 必需信息 |
| --- | --- |
| 发布身份 | 发布号、构建号、创建时间、状态、上一可用版本 |
| 代码与环境 | Git 提交或完整源码快照、运行镜像、依赖、字体和转换工具版本 |
| 语料范围 | 文档族、修订、资产、使用状态、排除和延期记录 |
| 处理契约 | Schema、解析、OCR、切块、位置映射和资格策略版本 |
| 检索配置 | 两路模型、passage 契约、集合、路径、父块集合及各路点数 |
| 回答配置 | 生成与重排模型、提示词版本、证据预算、范围策略 |
| 验证材料 | 题集修订、解析复核、索引核对、语义评分、阅读器检查 |
| 运维信息 | 运行目录、挂载、端口、日志位置、回滚目标和验证结果 |

模型、字体和依赖使用可复现的已安装版本，不要求在本次扩库中升级到最新版本。既有模型及索引契约继续使用；只有契约确实改变时才生成新身份。

### 10.4 一致性要求

两路向量索引必须覆盖同一套合格父块，且相同父块的正文、修订和位置一致。每路点数分别匹配自己的构建结果，不比较两路点数是否相等。

BM25、目录和阅读器都从同一发布快照初始化。当前运行时由索引重建目录，只会看到可检索文档；新目录应来自发布清单，以展示附件和暂不可检索的资料。

从清单移除的修订必须在新候选中真正退出相应检索范围。现有脚本不会自动删除登记表外残留的文档，因此需要验收“预期修订集合与实际索引集合相符”，不能只核对新增数量。

本地 Qdrant 目录由单个构建或服务进程占用。优先从规范证据新建候选；必须复制旧索引时，先停止占用进程或使用已验证的一致性副本。禁止复制正在写入的目录，也禁止候选与正式服务共用可写索引。

## 11. 验证设计与上线门槛

### 11.1 验证集组成

保留既有 50 题作为开发与回归资产。补充本批资料的格式、版本和业务任务，不将同源改写题包装成独立科研测试集。

建议新增 60 题，作为首版验收集的规划值。具体题目在代表样本解析后冻结，至少包含以下分组：

| 分组 | 计划题数 | 验证重点 |
| --- | ---: | --- |
| 新资料事实与操作 | 20 | 标准、IOC、定时、联锁、数据存储等，跨主要格式 |
| 当前、历史和版本比较 | 15 | 新旧参数、部分替代、不同设备版本 |
| OCR、表格、幻灯片与公式 | 15 | 数值、列关系、备注、来源位置和表达保真 |
| 冲突、未知与资料边界 | 10 | 待核实日期、未批准修订、设计与现场、缺证据 |
| 合计 | 60 | 与旧 50 题分别报告，并给出组合结果 |

新增题中，约 40 题用于开发诊断，20 题在提示词和检索策略调整前封存，由业务审核人出题或确认。封存题一旦用于调参，就退回开发集，并补充新的封存题。

每题附任务条件、预期答案边界、必要事实、禁止推断、来源修订、证据位置和同源分组。标注用例覆盖已有资料、已收录新资料、历史资料和明确未收录资料。

新增资料可能让旧版的拒答题变成可作答题，也可能补充旧答案的适用条件。因此，旧题保留原始题集与评分记录；另建绑定 `kb-2.0.0` 语料范围的期望答案修订。评分变化必须由新增证据解释，并在候选问答前冻结，不能为了提高得分事后修改答案。

### 11.2 工程门槛

以下是本计划提出的首版验收门槛，并非已达到的结果。实施启动时确认，不能在看到候选成绩后降低门槛。

| 验收对象 | 通过要求 | 未通过时 |
| --- | --- | --- |
| 资料盘点 | 218 个文件均有处置；原有 17 份迁移有记录 | 补齐去向，不按文件总数宣称完成 |
| 元数据 | 所有上线修订具备身份、来源、范围、状态和责任记录 | 暂存缺失项或修复 |
| 关键内容 | 验收涉及的参数、单位、比较关系、步骤和表格映射全部复核通过 | 修复解析或移出对应承诺范围 |
| 版本规则 | 版本专项题中没有将不适用旧版、草稿或未知部署状态说成当前事实 | 阻止发布并定位过滤或生成问题 |
| 原有能力 | 原有已正确案例无新增关键错误；一般退化逐题裁决 | 修复，或明确缩小变更范围 |
| 新增问答 | 新增可作答题的人工任务通过率目标至少 90%；版本与边界关键题必须全部通过 | 修复后重验受影响分组 |
| 引用 | 自动检查所有返回引用可定位；验收关键断言均有人工确认的支持证据 | 修复引用或答案 |
| 索引 | 两路父块集合及内容一致，修订范围正确，各路点数符合清单 | 候选作废，不允许只发布成功的一路 |
| 阅读体验 | 首版各格式均可打开、定位，公式与表格可读；旧引用按策略解析 | 修复阅读器或调整资料展示方式 |
| 运行性能 | 同环境、同并发下，P95 响应时长目标不超过重新测得基线的 1.3 倍，且不触发现有请求超时 | 先分析瓶颈，不能只放宽预算 |
| 发布恢复 | 候选启动、生产切换和回滚演练通过 | 暂停上线 |

“任务通过”要求必要事实、条件和结论均正确，且没有禁止推断。关键错误包括错误参数、错误操作顺序、错误适用版本和无依据的现场状态断言。一般措辞问题不能与关键错误混为一个总分。

90% 是上线质量目标，不是预测准确率，也不证明研究方法有统计显著收益。实际报告给出每组题数、通过数、失败案例和审核分歧。与旧库比较时，区分旧库无证据和旧库答错。

### 11.3 测试与人工复核分工

自动测试重点覆盖真实失败模式：旧 ID 被覆盖、同页扩展越过修订、退出资料残留、表格定位错位、候选配置只切换一路、旧引用指向新原文。解析器测试使用少量经人工核对的代表样本，不为每个文件复制同样的测试。

人工复核覆盖所有关键版本案例和发布验收答案。至少由一位熟悉资料的业务审核人完成语义评分；版本冲突、数值争议和评分分歧再由第二位审核人裁决。助理生成的评分只能作为待复核意见。

基线与最终候选各执行一次固定条件的完整问答；中间修复优先重验受影响分组。只有最终候选再次变化或发现关联风险时，才补跑必要回归，避免重复问答选取更好结果。

现有 2026 年 10 月 30 日 P95 为 31.0 s，仅作历史参考。正式性能比较使用同一机器、模型服务和并发条件下的新基线，并记录加载时间、内存、磁盘和生成服务调用数。拿不到的资源指标标为未测。

## 12. 生产上线与回滚

### 12.1 上线前准备

上线前核对实际运行版本，冻结最终候选和回滚目标。现有记录中的 Markdown 发布目录为 `/opt/accelerator-rag-releases/md-20261030`；是否仍在服务，以届时现场状态为准。

新版本的回滚目标应是切换前确认可用的完整版本。不能直接沿用旧手册中仅含 13 份 PDF 的容器作为本次默认回退点，也不能因旧容器仍存在就认定它可恢复。

准备候选代码、原文、派生资产、元数据、两路索引、配置和运行环境；检查实际磁盘与内存余量。若新旧 RAG 无法同时驻留 GPU，则采用维护窗口切换，不承诺零停机。

服务器连接优先使用现有授权方式。若实施时需要读取 `/home/whloong/projects/secret.txt`，必须在本次读取前取得用户明确审批；不把凭据放入发布包、报告或日志。

### 12.2 候选验证与切换步骤

1. 将最终候选放入独立发布目录，完成路径和挂载检查。
2. 使用候选配置启动临时服务，在资源允许时选择临时端口；资源不足时安排受控验证窗口。
3. 验证发布身份、文档目录、原文、各类引用和代表问答，确认运行的就是冻结候选。
4. 从当前稳定包演练恢复，记录停止、启动、模型加载和恢复访问的实际时长。
5. 由发布负责人记录验收结论、切换时间、值守人和回滚目标。
6. 停止旧 RAG，保留其目录、配置与可恢复运行方式；将正式入口切到候选版本。
7. 检查正式入口的发布号、健康状态、目录数量、原文阅读和固定冒烟题。
8. 进入上线观察期，记录实际问答异常和处理结果。

切换仅管理本次 RAG 服务及其挂载和入口。沿用已有生成服务，是否需要重启其他组件应由实际变更决定。

现有 `deploy/rag-start.sh` 固定容器名，且会删除同名容器。发布前需补充明确的候选、保留旧版和恢复路径，或提供专门发布脚本，不能把当前启动脚本当成已经实现的蓝绿切换工具。

### 12.3 回滚触发与动作

出现以下问题时，停止推广并回退：发布身份不一致、两路语料不一致、原文引用普遍失效、关键任务出现错误版本或错误参数、服务无法稳定启动，或持续超时影响正常使用。

回滚步骤如下：

1. 停止新 RAG，保留故障版本、日志和相关请求记录。
2. 恢复上一稳定版本的代码、配置、元数据、原文与两路索引。
3. 恢复其正式入口，检查发布号、目录、原文和固定冒烟题。
4. 记录回滚原因、实际恢复时间和受影响范围。
5. 在新候选中修复问题，产生新的发布号，不直接修改已失败的冻结版本。

首版恢复时间目标暂定为 15 min 内，以演练结果校准。若模型加载或环境恢复无法达到该目标，应在上线前明确实际窗口并改进操作，不以未经测量的时间作承诺。

### 12.4 观察与收尾

观察期建议为 2 个工作日，覆盖至少一个正常使用周期。检查接口失败、超时、引用失效、版本误用和新增主题的检索失败，保留有诊断价值的请求记录。

新版本稳定并完成验收后，至少保留上一完整可用版本 30 天；具体保留期以磁盘和项目要求确认。用于历史引用和研究复现的源修订继续保留，不因清理运行目录而删除。

只有完成观察、验收记录和维护交接，才把 `kb-2.0.0` 标记为正式完成。上传文件、建完索引或健康检查通过均不是最终完成条件。

| 存储 | 原件、阅读副本、规范证据、两路索引、临时转换文件和日志 | 同时容纳稳定包、候选包、回退包及必要构建空间 |
| 问答验证 | 每题耗时、模型调用数；可获得时记录输入输出 token | 按冻结题集估算验证时间，避免重复全量请求 |
| 人工审核 | 每类资料和每类题的复核时间、分歧数量 | 优先确认版本与关键参数，预留争议裁决时间 |

在已有模型、算力和转换环境满足要求时，不默认采购外部服务。需要新增 OCR 或解析服务时，先核对资料能否发送、实际单价和样本效果，再提交费用与范围变化。资源不足时优先调整构建批次与时间窗口，不挤占生产问答所需资源。

## 14. 主要风险与范围控制

| 风险 | 具体影响 | 控制方式 |
| --- | --- | --- |
| 权威版本未确认 | 把通读稿或未来日期资料当现行规范 | K0、K1 核对；待核实材料限定用途 |
| 旧版与新版共用文档 ID | 更新时删除历史版本 | 修订独立身份，先完成迁移契约 |
| 大文档转换或 OCR 失真 | 参数、公式、表格关系错误 | 代表样本测量，关键内容人工核对 |
| 只检查新增文件 | 原有资料遗漏或退出资料残留 | 按完整发布清单核对实际修订集合 |
| 过滤只作用于一条检索路径 | BM25、邻接补全或补检索带回旧版 | 使用统一范围并测试所有路径 |
| 日期较新压过更适用资料 | 设备或版本错配 | 先判适用范围，再比较来源和修订关系 |
| 扩库后候选竞争加剧 | 旧任务回归、证据预算不足 | 在固定预算下诊断召回和选择，按测量调整 |
| 新旧原文和索引不同步 | 引用打开错误内容 | 发布包成套切换，引用绑定发布与修订 |
| GPU、磁盘或审核资源不足 | 构建和上线延期 | 样本阶段估算，提前预约；延期范围写明 |
| 新题与开发过程同源 | 高分不能代表独立泛化能力 | 开发、封存和研究测试分开报告 |

首版不把知识图谱、通用 Agent、全自动知识失效传播、全图纸理解、网页在线上传和实时控制接入一并纳入。后续能力通过真实任务和测量结果单独立项，避免扩建计划失去可验收边界。
