# 需求约束的 RAG 证据闭环

## 实现范围

本流程按四个阶段组织：问题解析、多路召回、证据子集选择、证据核验与受控生成。未覆盖的子需求进入定向补检索，达到预算后返回完整回答、部分回答或拒答说明。

系统使用原始工程资料回答问题。问题中的功能假设不自动成为事实。例如，资料只说明信号转换功能时，回答应解释该作用，不能将其升级成独立的快速保护逻辑。

## 问题解析与子需求拆解

`rag/answer.py` 中的 `extract_requirements` 在检索前运行。它只接收原问题，输出 1 至 6 个子需求。每项保留原语言问句，并提供英文检索问法。

关系要求单独保留。例如，“组件各自的作用”和“组件之间如何协作”不能合并成一个组件的响应时间。检索问法不得猜测答案、具体数值或未获证实的设备功能。

## 多路召回与候选生成

`rag/retrieval.py` 中的 `RequirementRetriever` 分别检索原问题和子需求。当前实现保留既有 E5、Qwen3 双路语义检索与 Qwen3 重排，并增加 BM25 词法检索。不同通道的原始分数不直接相加，候选融合使用排名。

程序沿已命中文档的相同版本、相同物理页补取关联父块，避免同一节跨块后丢失前置连接说明。候选统一去重，再用重排模型评分。每轮最多保留 20 个候选父块；候选上下文最多包含 18,000 个 token。

BM25 在启动时从已签名索引中的规范父块构建内存索引。程序不改变分块、不重算向量，也不写入正式向量索引。

## 需求约束的证据子集选择

模型先逐项判断候选证据能回答什么、还缺什么，并标出不能同时采用的冲突来源。程序验证所有片段和来源 ID，拒绝虚构引用。

每项需求可以包含一个首选充分组合和最多 3 个等价组合。保留其中一组即可覆盖该项；多对象或多版本问题的每组都必须覆盖全部所问条件。程序不会把同义描述和非必要实现细节全部当作必须同时保留的证据。

字段和清单问题先从候选正文建立条目清单。每项绑定可区分该项的原文短语及实际出现的片段。程序验证原文锚点，并要求充分组合覆盖每个条目；摘要的几类概述不能替代更详细的登记字段。

数值要求的替代组合保持首选组合的文档和版本范围，不能仅因旧版材料更短而替换定义。用户未指定版本时，优先匹配对象与工程阶段，再考虑最新正式资料；不同不等号或参数定义不视为等价。

`rag/evidence.py` 中的 `choose_subset` 在有限候选中枚举子集，优先提高完整覆盖，再考虑部分覆盖、重复内容与上下文成本。互相冲突的来源不能同时入选。不同年份本身不代表冲突；用户要求版本对比时，应分别保留各自口径。对明确要求对照年份或版本的问题，程序将已知不同版本之间的分歧记为 `scope_differences`，不按互斥冲突排除；同版本冲突和未明确比较版本的问题仍使用冲突约束。输出继续分别绑定来源，不能据此把不同参数定义合并。

当前子集约束为最多 5 个父块、证据上下文最多 6,000 个 token。使用本地 Qwen3 重排模型的 tokenizer 统一计量。成本估算采用各记录的保守累计值，接受子集前再次计算实际序列化上下文的 token 数。

这项预算约束的是所选证据上下文，不是生成模型的完整请求或计费 token 数。系统提示词、问题和结构化协议另有开销；生成模型的 tokenizer 也可能不同。

这实现了图中的覆盖、冲突和开销约束。搜索范围是本次有限候选，并非整个语料库；保守成本与来源数量上限也会限制可行集。因此，不宣称实现了全语料范围的理论最优解。

选中子集继续使用原来的来源和片段 ID。裁剪上下文不会改变引用身份。子需求之间可以联合使用已验证事实，但每条结论必须显式绑定证据，并接受最后的语义核查。

## 核验、生成与反馈

`rag/workflow.py` 执行有界闭环。证据未完整覆盖子需求时，程序针对缺项生成最多 3 个补充查询，再次召回和选择。默认最多执行 2 轮检索。

证据足够时生成答案；达到检索上限后，也可以生成有依据的部分回答。生成阶段只能使用已选择并验证的事实。完整父块用于理解指代和关系，不能作为随意添加新参数的理由。

最终核查分别判断两个问题：每条结论是否有依据，以及每项需求是否已经答全。失败时给出具体原因和缺项，并允许一次语义重写。结构化输出不符合契约时，另允许一次契约修复。

核查通过的事实会保留。某项需求不完整，不再导致该项的真实事实全部消失。如果答案依据证据纠正了问题前提，且最终核查认可其完整性，状态会更新，不再沿用初始的不支持判断。

具体数值、逐项接线或完整清单采用更严格的完成条件。初始证据仍有缺项时，回答“资料未给出”不能把该项升级为完整回答；程序保留缺项和已确认事实。职责类问题的前提纠正与实际数据缺失分别处理。

数值、版本或图表编号校验按结论执行。数值比较归一化前导零和无效末尾零，避免把版本日期中的 `07` 与正文的“7 月”误判为新增数值；设备及图表标识符仍单独核对。存在其它有效结论时，只剔除不可靠结论，再核查剩余正文的完整性。剔除一条结论不会自动判定问题已经答全，仍可能触发重写、补检索或部分回答。

补检索使用缺项和核查原因作为线索。历史回答和核查意见不作为新证据。实时运行数据仍受确定性边界保护，静态设计文档不能证明当前读数。

## 响应与可溯源性

每条关键结论绑定本次请求中真实存在的片段。来源编号、文档版本、物理页和原文摘录由代码解析生成。版本或参数定义不同的证据分别注明口径。

工程数值按文档和版本拆成独立结论。跨版本关系可以联合解释，但不能把不同来源的数值写成一个混合结论，也不能因为数值相同就宣称运行口径相同。

状态含义如下：

| 状态 | 含义 |
| --- | --- |
| `answered` | 最终核查确认所有子需求都已完整回答。 |
| `partial` | 仍有子需求未完整回答，但存在核查通过的事实。 |
| `insufficient` | 没有可展示的已核查事实，返回缺证据或实时能力边界说明。 |

`requirements[].supported` 表示最终完整性。`coverage` 进一步区分 `complete`、`partial` 和 `none`；`reason`、`missing` 记录判断原因及具体缺项。完整回答的 `missing` 为空。

每次响应增加 `request_id`。配置 `trace_dir` 后，服务端保存拆题、逐路召回、候选、证据选择、预算、冲突、模型调用、重写和最终结果。记录文件权限为 `600`，保留最近 100 份；没有公开的记录下载接口。

## 验证标准

验收检查实际行为，不能仅凭接口返回成功或状态为 `answered` 判定通过。

- 拆题先于检索，组件职责和关系要求均进入检索。
- 缺项触发定向补检索，而不是重复整个泛问题。
- 低排名的必需证据能进入子集，冗余高排名材料可以排除。
- 来源冲突、数量上限和实际 token 预算均受到约束。
- 联合证据可以支持关系说明，未验证片段不能混入答案。
- 错误结论被删除，已确认的部分事实得到保留。
- 原问题、自然改写、版本对比、实时问题和真实资料缺失均有回归记录。

覆盖和语义判断仍依赖模型。生成与核查是独立调用，但使用同一模型服务；有限候选、检索轮数及上下文预算也可能造成漏项。这些限制应在真实问题验收中持续评估。
