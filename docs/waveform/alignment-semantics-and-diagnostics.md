# 对齐语义、参数与诊断手册

多台 BPM 的文件都有数据，并不意味着可以直接逐点比较。它们可能记录了不同的编号范围，缺少不同的点，或采用不同的编号规则。对齐的作用，是先确定哪些记录可以按相同编号放在一起，再把这些记录交给绘图或分析。

本文帮助你完成一次对齐，判断结果是否适合分析，并在共同点不足时找到下一步检查方向。尚未确定任务和数据段时，先阅读[存储与数据流说明](waveform-storage-dataflow.md)。

## 1. 对齐到底做了什么

<a id="2.1"></a>

当前系统以 `bunchID` 的整数值相等作为匹配条件。它不移动波形、不按相近编号凑点，也不根据峰形寻找时间偏移。

以下是用于解释规则的简化示例：

| 设备 | 原始 bunchID | 严格对齐后保留 |
| --- | --- | --- |
| A | `2, 4, 6` | `2, 6` |
| B | `2, 6, 10` | `2, 6` |

输出中，编号 `2` 对应一列，编号 `6` 对应另一列；每台设备的 X、Y 数值跟随原编号进入相应位置。两台设备的步长不同，仍可能有共同编号。

**编号匹配解决的是数据组织问题。** 如果要把同一列解释为同一个物理事件，还需确认设备共享可比较的编号规则。仅凭对齐成功，不能证明设备在物理时间上同步。

## 2. 按这个顺序完成一次对齐

<a id="3.1"></a>

### 2.1 确定本次分析需要哪些数据

先选定一个 `request_id` 和一个 `capture_sequence`，再选择设备。写清本次分析目的：是要求所有目标设备逐点比较，还是允许部分设备缺点？这会决定后面能否使用覆盖率模式，以及结果怎样解释。

核对所选设备是否都取得文件。下载失败、文件缺失和格式异常应保留在记录中，不能在对齐后只看剩余设备，误认为全部目标设备都参与了分析。

### 2.2 查看原始编号，再运行算法

检查各设备的点数、编号起止值、重复编号和相邻编号步长。如果某台设备与其余设备明显不同，先确认是否选错段，再查设备的编号约定。

正式界面的原始步长预检查会提示异常，要求确认后再继续。它帮助暴露差异，不会自动修正编号，也不会自动删除异常设备。步长相同也不代表窗口一定重叠，还应查看编号范围。

### 2.3 先用严格模式了解共同数据

<a id="3.3"></a>

`strict` 保留所有通过预处理的设备共有的编号。对于要求同一组设备逐点比较的任务，可以先运行它，观察实际共同点数量和设备名单。

这里的“所有设备”指通过预处理的设备。重复编号、非法数组等问题可能导致某台设备被跳过。因此，严格模式完成后仍要看 `skipped_devices`，不能把输出自动解释为“覆盖了请求中的全部设备”。

### 2.4 必要时使用覆盖率模式

<a id="3.4"></a>

`coverage` 适用于允许部分缺失的任务。它先按设备覆盖比例筛选候选编号，再检查每台设备是否覆盖了足够多的候选编号；移除不满足条件的设备后继续计算，直到结果稳定或没有可保留的数据。

例如，三台设备中允许某个编号只出现在两台设备上，就可能保留严格模式会舍弃的编号。但缺失位置仍然缺失，后续处理必须读取 `valid_mask`。如果某项分析要求所有设备同点有效，就不能仅靠放宽覆盖率来满足它。

两个覆盖率阈值默认都是 `1.0`。仅把模式切换成 `coverage`，保留这些默认值，通常不会增加共同编号。阈值应由分析要求决定，不以“留下更多点”为唯一目标。

## 3. 对齐完成后，怎样判断能不能用

先检查设备，再检查点，最后检查分析条件。

| 检查对象 | 要回答的问题 | 结果如何影响下一步 |
| --- | --- | --- |
| `device_ids`、`skipped_devices` | 必需设备是否都在？哪些设备被跳过，为什么？ | 必需设备缺失时，先处理缺失或调整研究范围 |
| `bunch_ids` | 共同点有多少？覆盖的编号范围是否合理？ | 点数过少时，检查原始窗口和限制交集的设备 |
| `valid_mask` | 各设备在哪些位置有真实数据？ | 计算统计量、绘图或频谱前应用掩码 |
| `quality_report` | 是否存在重复、乱序或覆盖不足？ | 判断这些处理是否符合本次分析要求 |
| 时间轴、单位与分析配置 | 频率来源是否可靠？有效跨度够不够？ | 通过对齐后，再决定是否可以进行目标分析 |

覆盖率输出中，缺失位置的 X、Y 可能填为 0，只有 `valid_mask` 能区分占位值和真实零值。直接对整个数组求均值、做频谱或比较幅值，会把缺失值当成观测值。

输出设备按 `device_id` 排序。使用矩阵时应依据输出的 `device_ids` 对应行，不能沿用最初勾选设备的顺序。

### 3.1 导出时保留哪些信息

需要保留缺失掩码、对齐参数和质量信息时，使用 v2 HDF5。Legacy 格式不能表达缺失位置，但覆盖率结果如果所有位置都有值，并非一概不能写成 legacy。

应用服务在查询包含 `request_id` 时会使用 v2 导出。分析和归档时还应保存任务 ID、段序号、请求设备、实际设备及参数，便于解释为什么得到这一组结果。

## 4. 为什么有数据，却不能直接做频谱

<a id="4.6"></a>

### 4.1 相对时间轴依赖两个前提

分析器根据编号的典型步长和采样率建立相对时间轴。当前加载器要求编号为递增、无重复、非零的整数，并检查相邻差值是否符合推断出的步长。

采样率优先来自历史任务记录。缺少记录时，需要有依据的补充信息，不能拿当前 timing PV 的值解释过去的数据。编号的典型步长也需要对应真实采样周期；算法从数组推断出步长，不代表已经验证了设备时基。

当编号缺口是所推断步长的整数倍时，加载器可以在时间轴上保留这个间隔。如果数据整体已经稀疏到把较大的间隔当成基本步长，单靠现有编号可能无法识别中间遗漏了多少采样。

### 4.2 起点都是 0，不代表原始时刻相同

加载器先以输出编号序列的首点建立统一相对时间轴。分析准备阶段会应用每个通道的有效掩码，并把该通道的首个有效点移到 0，同时记录 `first_valid_offset_seconds`。

因此，两个通道最终都从 0 开始，原始首个有效时刻仍可能不同。比较跨设备相位、时延或相关性时，应保留偏移信息，或选择共同有效区间，不能只比较各自归零后的横轴。

<a id="4.7"></a>

### 4.3 点数、跨度和缺口要一起看

频谱分析还有独立的质量要求。例如，默认 `high_band` 配置要求至少 128 个有效点和 5 s 的有效跨度；其他分析配置可能要求更长的记录。应以本次分析配置为准。

分析层可以在规则时间网格上插值，但会检查缺口，默认 `max_gap_factor` 为 `5`。插值发生在分析准备阶段，不改变前面的编号匹配规则。它也不能恢复未观测到的物理过程。

<a id="4.10"></a>

幅值解释还需要单位与标定关系。`bunchID` 没有秒或 Hz 的单位；原始 X、Y 的物理单位不能仅由数组类型推出。

## 5. 共同点太少时，怎样找原因

<a id="5.1"></a>

### 5.1 从输入范围逐步缩小问题

1. 确认所有文件来自同一任务、同一数据段。
2. 比较原始编号起止值，判断各设备是否覆盖同一个窗口。
3. 查看点数、重复编号、零编号和步长分布。
4. 以单设备或已知可比较的设备组作为参照，逐步加入其他设备。
5. 必要时做逐台排除的诊断比较，记录哪台设备加入后共同点明显减少。

逐台排除用于定位影响，不等于决定研究中应删除该设备。最终设备范围要由分析目的和编号的物理含义决定。

### 5.2 一个真实例子：25 台都有数据，交集却只剩几百点

2026-10-12 的任务 `22833275-5e77-41c5-b703-f306accde164` 有 5 段数据，每段 25 台设备各 20000 点。严格对齐后，五段分别只剩 422、621、455、375、288 个共同点。

进一步比较发现，`AC_LA_L1_BI_COLDBPM05` 的编号步长为 28–76，其余 24 台为 2000。诊断时排除该设备，共同点恢复到每段约 19500 个。这定位了限制交集的设备和编号差异，但还不能断言该设备损坏，或已经找到了硬件层根因。

按当前加载器和任务记录的 500 Hz 推算，原严格结果的跨度只有 0.574–1.240 s，达不到默认 `high_band` 的 5 s 要求。此时应先解决数据可比性和分析范围，不能通过修改时长标签来使数据“合格”。完整记录见[case-07](fault-history-and-version-changes.md#case-07)。

### 5.3 常见现象与处理

<a id="5.3"></a>

| 现象 | 如何理解 | 处理方向 |
| --- | --- | --- |
| 共同点为 0 | 当前设备组没有精确共有编号 | 查任务和段、编号窗口、编号约定；空交集本身是有效诊断结果 |
| 步长不同 | 编号序列存在差异，仍可能有交集 | 同时看范围和交集，不直接判定设备故障 |
| 编号重复 | 同一设备一个编号对应了多条记录 | 默认跳过该设备；有理由采用首条时再改策略，并记录选择 |
| 编号乱序 | 文件记录顺序与编号顺序不同 | 对齐会排序；结合原始步长诊断判断乱序来源 |
| 有编号 0 | 当前数据含零编号 | 根据数据约定选择保留、丢点或跳过设备；分析层有额外限制 |
| coverage 后出现很多零值 | 可能包含缺失位置的占位值 | 先读取 `valid_mask`，再解释数值 |
| 对齐成功、分析拒绝 | 两个阶段的输入条件不同 | 查有效点数、时间跨度、频率和缺口 |

某台设备多出一个编号 0，不会必然缩小非零编号的交集。例如，`0, 2, 4` 与 `2, 4` 在保留或丢弃 0 时，共同编号都是 `2, 4`。处理零编号前应先确认它实际影响了什么。

## 6. 参数与采集条件参考

<a id="4.1"></a>

### 6.1 对齐参数

| 参数 | 默认值 | 可选值或范围 | 用途 |
| --- | --- | --- | --- |
| `mode` | `strict` | `strict`、`coverage` | 选择精确交集或允许部分缺失的模式 |
| `min_id_device_coverage` | `1.0` | 大于 0 且不超过 1 | coverage 中，一个编号至少需被多少比例的活动设备覆盖 |
| `min_device_id_coverage` | `1.0` | 大于 0 且不超过 1 | coverage 中，一台设备至少需覆盖多少比例的候选编号 |
| `zero_policy` | `keep` | `keep`、`drop`、`reject_device` | 处理 `bunchID == 0`，不是处理 X、Y 的零值 |
| `duplicate_policy` | `reject_device` | `reject_device`、`first` | 跳过含重复编号的设备，或保留原输入中第一条对应记录 |

strict 不使用两个覆盖率阈值筛选数据，但参数构造时仍校验其范围。非法模式、策略或阈值会抛出 `ValueError`。

分析配置也有名为 `zero_policy` 的参数，其 `mask_double_zero` 处理 X、Y 同时为 0 的记录。它与上表的编号零值策略属于不同阶段。

<a id="4.8"></a>

当前对齐参数没有时间容差、编号容差或自动缩放系数。如果设备编号需要转换，应先确认转换依据，并将转换作为独立处理记录下来。

### 6.2 采集条件如何影响对齐输入

采集频率、等待值和触发属于对齐的上游。支持的频率及周期等待表见[存储说明第 3 节](waveform-storage-dataflow.md#3-采集请求如何变成文件)。

当前服务端在受理新请求时读取 timing PV。`FREQUENCY_MISMATCH` 表示请求频率与读取值不一致；`TIMING_FREQUENCY_FAILED` 需要结合错误信息检查读取失败或不受支持的档位。该检查不是整个采集期间的连续频率监控。

采集触发通过 EPICS 对 `capture_pv` 执行置 1、等待、再置 0 的过程，默认触发等待为 5 s。协议没有供操作员选择的多种触发模式。软件发出了触发，也不能单独证明所有设备在同一物理时刻采样。
