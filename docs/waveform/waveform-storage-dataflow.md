# Waveform 存储与数据流技术说明

一次采集完成后，最先需要弄清的是：采到了哪些设备、分成了几段、哪些文件可以一起使用。本文沿着这条线索，说明如何找回数据、识别缺失，以及理解文件中的编号和时间。

本文面向采集操作员、数据分析人员和维护人员。已经找到数据、准备进行多设备分析时，接着阅读[对齐语义、参数与诊断手册](alignment-semantics-and-diagnostics.md)。

## 1. 先把一次采集看成“任务、数据段、设备文件”

一次采集请求对应一个任务。任务运行期间可以产生多个数据段；每个数据段中，每台成功采集的 BPM（束流位置监测器）保存一个 HDF5 文件。设备失败时，该段可能只有部分设备的文件。

例如，一个任务选择了 20 台设备，共产生 3 段数据。第一段可能有 20 个文件，第二段只有 18 个，第三段又有 20 个。分析第二段时，应先查明缺少哪两台设备，再决定这段是否满足分析需要。任务状态和文件数量都要看：任务失败，也可能已经留下可用文件。

<a id="3.1"></a>
<a id="3.2"></a>

| 你想确定什么 | 使用的标识 | 怎么理解 |
| --- | --- | --- |
| 是哪一次采集 | `request_id` | 一次任务的 UUID；查询、状态跟踪和重试使用同一身份 |
| 是任务中的哪一段 | `capture_sequence` | 从 0 开始的段序号；只有和任务 ID 一起使用才有明确含义 |
| 是哪台设备 | `device_id` | 设备注册表中的 BPM 标识 |
| 是文件中的哪个记录 | `bunchID` | 随波形保存的非负整数编号；解释它的物理含义需要设备侧约定 |

**定位一份原始波形，要保留任务 ID、段序号和设备 ID。** 日期和时刻适合帮助人查找，但同一天同一秒可能存在不同任务，不能单独充当数据身份。

不同数据段之间可能存在等待、下载或失败造成的间隔。系统按段读取和分析，不自动把多段拼成连续波形。确需跨段研究时，应先确定段间时间关系和汇总方法。

## 2. 找回一次采集的数据

<a id="6.1"></a>
<a id="6.2"></a>

### 2.1 优先按任务和数据段查询

历史数据查询按以下顺序进行。界面的具体布局可能随版本变化，选择逻辑不变。

1. 按采集日期找到任务，核对 `request_id`、区域、设备范围和频率。
2. 查看该任务的数据段列表，选择一个 `capture_sequence`。
3. 比较请求设备与该段实际保存的设备，查看失败原因。
4. 读取所选设备的文件，确认设备身份、数组长度和点数。
5. 将同一段的数据交给对齐流程，并保留未取得文件的设备名单。

通过协议接口完成这项工作时，依次使用 `list_capture_runs`、`list_capture_segments` 和 `find_waveform_files_by_segment`。最后一步按任务、段和设备查找文件路径。

### 2.2 旧数据只有日期和时刻怎么办

旧接口 `list_capture_times` 和 `find_waveform_files` 仍然存在，按日期、时刻和设备查询。使用它们时，要额外核对文件中的采集元数据，避免把不同任务的同一时刻文件混在一起。

有些搬运过的历史样本没有完整元数据目录，只能从文件名和 HDF5 属性恢复部分信息。此时应记录“任务身份不完整”，不要仅凭文件名相似就把数据合为一段。

### 2.3 历史页查不到，是否说明数据丢了

先区分“目录查不到”和“文件不存在”。MongoDB 保存任务及文件目录，HDF5 保存波形数组。元数据写入失败不会阻止已经完成的 HDF5 落盘。

遇到 `METADATA_UNAVAILABLE`，先检查元数据服务是否启用、是否可连接。需要通过旧 SSH 目录扫描路径找文件时，仍须核对文件身份；目录扫描不能补回缺失的任务记录。已经有精确路径但文件读取失败时，再检查存储连接、路径和 HDF5 内容。

## 3. 采集请求如何变成文件

<a id="2.1"></a>

| 环节 | 系统做什么 | 操作员应关注什么 |
| --- | --- | --- |
| 受理请求 | 校验设备范围、请求时长、频率及注册表快照 | 请求被接受只表示任务已受理 |
| 检查频率 | 读取 timing PV，并与请求频率核对 | 不一致时先查机器当前状态和请求来源 |
| 执行一轮采集 | 触发 EPICS、等待设备产出、下载 TXT | 触发成功后，设备文件仍可能为空或未完成 |
| 解析和保存 | 检查点数与数据格式，写成单设备 HDF5 | 查看每台设备的成功或失败记录 |
| 登记目录 | 记录任务状态、文件路径和数组概要 | 目录故障与数据文件故障分别处理 |
| 开始下一轮 | 递增段序号，再执行采集 | 实际段数受等待、下载和任务窗口共同影响 |

正式文件通过同目录临时文件写入后替换生成。这个过程避免把正在写入的文件当成完整产物，但不能保证设备数据的物理含义正确。

### 3.1 三种“时间”分别表示什么

| 名称 | 表示什么 | 使用场景 |
| --- | --- | --- |
| 请求时长 `duration_seconds` | 任务计划运行的时间窗口 | 安排采集任务 |
| 周期等待值 | 程序按频率档位选择的采集等待时间 | 判断下一轮何时可能开始 |
| 分析数据跨度 | 分析器依据编号和采样率建立时间轴后得到的跨度 | 判断数据是否适合某项分析 |

这三者通常不同。长时间运行一个任务，不代表得到同样时长的连续波形；下载耗时也不属于波形采样时长。

### 3.2 频率从哪里来

在本文适用版本中，正式前端在启动和采集前读取 timing PV `AC-LA-INJ1-TIM:WRN1:MCFQ8`，服务端在受理新的采集请求时再次检查。这个机制检查的是提交时的频率，不能证明整个任务期间频率一直不变。

当前采集等待表如下。表中秒数是程序使用的等待值，不能当作相邻采样点的时间间隔，也不能自行在档位之间插值。

| 频率 | 周期等待值 |
| ---: | ---: |
| 1000 Hz | 2 s |
| 500 Hz | 4 s |
| 100 Hz | 12 s |
| 50 Hz | 22 s |
| 10 Hz | 2100 s |
| 5 Hz | 4200 s |
| 2 Hz | 512 s |

历史数据分析应使用任务记录的频率，并检查其依据。今天读取的 PV 值不能替代历史任务频率。历史记录缺失时，应先补充频率依据，再解释时间轴和频谱。

## 4. 打开文件后，先检查什么

### 4.1 原始 HDF5 的内容

| 位置 | 内容 | 读取时的意义 |
| --- | --- | --- |
| 根属性 `Device` | 设备 ID | 核对是否取到了目标设备 |
| 根属性 `Data_0`、`Data_1` | `bpm_x`、`bpm_y` | 确认两个通道的顺序 |
| 数据集 `BunchIDData` | 形状 `(1, N)`，`uint64` | 每个波形记录对应的编号 |
| 数据集 `Data` | 形状 `(2, N)`，`int64` | 第一行 X，第二行 Y |
| 根属性 `capture_metadata_json` | 采集元数据 | 核对任务、段、频率与采集时刻 |

生产采集写入的元数据包括 `protocol_version`、`request_id`、`frequency_hz`、`duration_seconds`、`capture_sequence` 和 `captured_at`。设备身份取自 `Device` 属性。

先确认 X、Y 和编号长度一致，再检查编号是否重复、是否乱序、是否有 0。原始文件可读不代表它满足后续对齐和分析条件；这些情况的处理见[对齐手册](alignment-semantics-and-diagnostics.md)。

### 4.2 编号和位置数值如何解释

`bunchID` 是整数编号。存储层不把它转换为秒，也没有为每个采样点保存独立时间戳。原始 X、Y 是整数数值；只有获得设备对应的单位和标定关系后，才能解释为物理位置。文件能读出数值，并不意味着单位已经确定。

<a id="6.3"></a>

时间轴由分析层建立。分析器使用编号步长和采样率推算相对时间，因此需要检查编号是否符合该模型。跨设备编号相同是否表示同一物理事件，还需要设备侧编号约定支持。

### 4.3 文件里的时刻是哪一个时刻

生产文件的 `captured_at` 是该段采集周期开始时刻，同段设备共享这个值。它不表示各设备每个采样点的实际采样时刻。

MongoDB 的 `created_at` 是记录写入时间，任务还有受理、开始和结束时间。分析采集发生时间时，优先使用带时区的 `captured_at`；旧文件缺少该字段时，元数据服务可能使用任务受理时刻作为回退，应保留这一来源差异。

## 5. 数据不完整时，沿哪条路径排查

| 看到的现象 | 先检查 | 下一步 |
| --- | --- | --- |
| 任务失败，但目录里有文件 | 逐设备结果与各段文件清单 | 保留成功文件，判断剩余设备能否支持本次分析 |
| 设备显示触发成功，文件却为空 | 设备侧 TXT 的大小、完成状态和时间 | 查设备产数与下载阶段，不先调整对齐参数 |
| 设备数齐全，对齐后点数很少 | 同段身份、原始编号范围和步长 | 转入对齐诊断，比较哪些设备限制了共同点 |
| 任务已完成，历史页查不到 | MongoDB 连接、登记记录、实际文件 | 分别修复目录与存储访问 |
| 显示时长与任务时长差很多 | 所选段、实际点数、频率来源、编号缺口 | 核对分析器时间轴，避免把任务窗口当数据跨度 |
| 重启后任务显示取消 | 任务状态历史与服务关停记录 | 按已保存文件清单判断产物，不假定任务完整 |

2026-10-02 的一次真实采集请求了 20 台设备，最后仅 2 台生成有效文件，任务状态为 `failed`。这个例子说明，定位问题应从“哪一段、哪台设备、在哪一步失败”开始。详细记录见[故障案例 case-02](fault-history-and-version-changes.md#case-02)。

## 6. 维护人员参考：路径、目录与版本

### 6.1 文件路径

生产文件默认写入 `/SHINE_Data/AC/LA`，可通过 `WAVEFORM_LOCAL_DATA_ROOT` 配置。路径模板为：

```text
{local_data_root}/{YYYYMMDD}/raw/BIData/RAW-{HHMMSS}-{device_id}-S{sequence:05d}.h5
```

设备 TXT 下载暂存路径为：

```text
{staging_root}/{request_id}/S{sequence:05d}/{device_id}.txt
```

文件名会被元数据登记和旧查询路径解析。维护时如需修改命名，应同时检查这些读取方。搬运过的样本可能采用扁平目录，应以实际文件及其元数据为准。

### 6.2 MongoDB 保存什么

| 集合 | 用途 |
| --- | --- |
| `capture_tasks` | 任务参数、状态、成功失败计数及版本信息 |
| `waveform_files` | 文件路径、形状、类型、点数和可用的单位信息 |
| `device_registry_versions` | 采集所使用的设备注册表快照 |

文件记录按任务、设备和段区分。为兼容旧记录，第 0 段的记录 ID 使用 `{request_id}:{device_id}`，后续段追加 `:S{capture_sequence:05d}`。MongoDB 不保存波形数组。
